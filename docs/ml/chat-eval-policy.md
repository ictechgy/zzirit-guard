# 채팅 평가셋 라벨 정책

- 대상: `workers/stage1/eval_data/`의 채팅 형식 개발셋·보류셋([모델 보강 계획](2026-10-14-model-strengthening-plan.md) M1)
- 왜 필요한가: 문장을 쓰는 사람과 라벨을 검토하는 사람이 같은 기준을 써야 숫자를 믿을 수 있다. 판정 기준은 [설계 스펙 §5.1](../superpowers/specs/2026-10-11-zzirit-guard-design.md)을 따른다. 매니저가 보고 숨기거나 조치할 만한 메시지가 `harmful`이다.

## 라벨

| 라벨 | 뜻 |
|---|---|
| `harmful` | 매니저 후보로 올라와야 하는 메시지. 자해는 숨김이 아니라 '도움 필요'로 올라와야 한다 |
| `allow` | 올라오면 안 되는 메시지 |
| `ambiguous` | 이 정책으로 정할 수 없는 메시지. 지표에서 뺀다. 전체의 5%를 넘지 않게 쓴다 |

## 유해 범주(`label: harmful`)

| 범주 | 정의 | 핵심 범주 |
|---|---|---|
| `abuse` | 스트리머·시청자 같은 특정인이나 집단을 향한 욕설·모욕·비하·혐오. 지역·성별·장애·외모·출신 비하 은어를 포함한다 | 아니오 |
| `sexual` | 성적 대상화, 성희롱, 성적 요구. **노골적인 묘사는 쓰지 않는다** | 예 |
| `minors` | 미성년자로 보이는 사람에게 접근하거나 유인하는 메시지(나이·학교 묻기와 함께 개인 연락·만남·사진 요구). **성적 표현은 쓰지 않는다** | 예 |
| `threat` | 신체 위해, 찾아가기, 스토킹 위협. "밤길 조심해" 같은 암시적 협박을 포함한다 | 예 |
| `doxxing` | 실명·주소·학교·직장·전화번호 같은 개인정보를 드러내거나 드러내겠다는 위협 | 예 |
| `self_harm` | 말하는 사람 본인의 자살·자해 의도, 계획, 방법 | 예 |
| `spam` | 광고, 도박·불법 사이트, 오픈채팅·텔레그램 유도, 상업 홍보 | 아니오 |

- 다른 사람에게 "죽어"라고 하면 `self_harm`이 아니라 `abuse`다. 행동 예고가 있으면 `threat`다.
- 한 메시지가 여러 범주에 걸리면 `minors` > `self_harm` > `threat` > `doxxing` > `sexual` > `abuse` > `spam` 순서로 앞의 것을 고른다. 예를 들어 주소를 드러내며 찾아가겠다고 하면 `doxxing`이 아니라 `threat`다.

## 허용 유형(`label: allow`)

| 유형 | 정의 | 예(형식만) |
|---|---|---|
| `friendly_profanity` | 감탄·칭찬·강조로 쓴 비속어. 모욕할 대상이 없다 | "방금 컨트롤 ○○ 미쳤네" |
| `game_combat` | 게임 속 공격·죽음·전투 표현 | "적팀 다 잡자", "저거 킬각" |
| `short_normal` | 짧은 인사·리액션·응원 | "ㅎㅇ", "오 굿", "화이팅" |
| `long_normal` | 일반 대화, 질문, 잡담 | 방송 내용에 대한 질문 |
| `quote_report` | 유해 표현을 인용·신고·비판하거나 부정하는 문장 | "방금 욕한 사람 신고했어요" |
| `number_url_like` | 점수·시간·버전·가격처럼 숫자나 점이 들어간 정상 문장 | "2:1 역전", "1.5배속" |

- 비속어가 들어 있어도 특정인을 깎아내리지 않으면 `allow`다. 같은 문장에 대상(스트리머, 시청자, 집단)과 비하가 함께 있으면 `abuse`다.
- 스트리머에게 하는 가벼운 장난("오늘 겜 왜 이럼 ㅋㅋ")은 `allow`다. 인신공격("머리 나쁜 ○○")은 `abuse`다.

## 작성 규칙

- 방송 채팅처럼 쓴다. 짧고, 띄어쓰기가 불규칙하고, 초성·반복 글자·이모티콘이 섞인다. 같은 틀에 단어만 바꾼 문장을 반복하지 않는다.
- 우회 표기(자모 분리, 숫자·기호 치환, 띄어 쓰기)를 범주마다 일부 섞는다.
- **실존 인물의 이름·연락처·주소를 쓰지 않는다.** 전화번호는 `010-1234-5678`처럼 누가 봐도 지어낸 번호를 쓰고, 주소는 실제 구·동 이름에 지어낸 번지를 붙인다.
- 문장마다 `family`(시나리오 계열)를 붙인다. 같은 상황에서 표현만 바꾼 문장은 같은 계열이다. 계열이 같은 문장은 같은 셋에 둔다.
  - 계열 이름은 작성 모델마다 따로 붙이는 이름이다. 그래서 '같은 계열'은 작성자와 계열 이름이 모두 같다는 뜻이다(`chat_eval_data`가 이렇게 검사한다).
  - 다른 모델이 우연히 같은 이름을 쓴 문장 사이의 누수는 문장 유사도 검사가 막는다.
- 72문장 회귀 세트(`docs/spikes/2026-10-11-guard-models/chat_samples.jsonl`)는 **열어 보지 않는다.** 그 문장을 보고 쓰면 평가가 부풀려진다. 겹침은 도구가 따로 검사한다.

## 파일 형식(JSONL, 한 줄에 한 문장)

```json
{"id": "dev-0001", "split": "dev", "label": "harmful", "category": "sexual", "family": "sexual-remark-appearance", "author": "<작성 모델>", "reviewer": "<검토 모델>", "text": "..."}
```

- `allow` 문장은 `category`에 허용 유형을 쓴다.
- `id`는 셋 안에서 겹치지 않는다. `split`은 `dev` 또는 `holdout`이다.
- 검토자는 작성자와 다른 모델이다. 검토자가 라벨이나 범주에 동의하지 않은 문장은 넣지 않는다.
